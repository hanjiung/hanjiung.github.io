**2026 캡스톤 프로젝트 · 팀장·PM · 마스킹·복원 개발**

고객 방문 일정을 정리해 달라는 요청에 전화번호가 들어 있다면, 외부 언어 모델(LLM)은 번호를 몰라도 답변을 작성할 수 있습니다. 우리 팀은 모델에는 `[PHONE_001]`처럼 바꾼 값을 보내고, 답변을 읽는 사용자에게는 다시 전화번호를 보여주는 프록시를 만들었습니다. 저는 팀장·PM으로 모델, 문서 파서, 웹의 연동을 조율하고 그 사이에서 개인정보를 가리고 되돌리는 코드를 작성했습니다.

## 내가 한 것
{: #my-work }

### 팀원들이 같은 입력으로 개발할 수 있게 한 일

모델, 파서, 웹 담당자가 서로의 구현을 기다리지 않도록 요청·응답 형식을 JSON Schema와 정상·오류 예시로 먼저 정리했습니다. 각 담당자는 같은 입력에 대한 모의 응답으로 개발을 시작했습니다. 저는 담당자와 마감을 정하고 연동을 막는 이슈를 추적했습니다. 실제 모듈이 준비되면 하나씩 교체해 회귀 테스트를 돌리고, 팀의 QA 결과를 모아 릴리스를 점검했습니다.

### 탐지 결과를 원문의 정확한 위치에 적용한 방법

전화번호·이메일을 찾는 정규식과 팀의 한국어 문맥 모델은 각각 개인정보의 시작·끝 위치를 반환합니다. 이모지 뒤의 이메일처럼 Python과 JavaScript가 문자 수를 다르게 셀 수 있는 경우를 고려해, 두 서버의 위치 단위를 **유니코드 코드 포인트**로 맞췄습니다. 프록시에서는 해당 구간을 잘라 탐지기가 보고한 원문과 일치하는지 확인합니다.

두 탐지기가 겹치는 구간을 고르면 더 긴 후보를 남기고, 길이까지 같으면 정규식 결과를 우선했습니다. 한 요청의 질문과 첨부 문서는 토큰 대응표 하나를 공유합니다. 같은 이메일이 양쪽에 나오면 둘 다 `[EMAIL_001]`이 되므로, 모델도 같은 연락처를 일관되게 지칭할 수 있습니다.

### 응답이 토큰 중간에서 끊길 때
{: #masking-example }

모델의 답변은 서버 전송 이벤트(SSE)를 통해 조각 단위로 옵니다. 저는 일반 문장은 즉시 보내고, 조각 끝이 등록된 토큰의 앞부분과 일치하면 그 부분만 잠시 보관하도록 구현했습니다. 논문 표 3.3-1의 예시에서는 두 조각이 이렇게 이어집니다.

| 도착한 응답 조각 | 프록시가 사용자에게 보내는 내용 |
| --- | --- |
| `담당자는 [PER` | ‘담당자는 ’을 먼저 보내고 `[PER`를 보관합니다. |
| `SON_001]입니다.` | 완성된 `[PERSON_001]`을 대응표에서 찾아 ‘김민수입니다.’를 보냅니다. |

## 웹 동작 과정
{: #web-demo }

팀이 개발한 웹에서 가상 고객 방문 문서 `CUSTOMER_D_005.txt`를 첨부하고 **“분석해줘”**라고 입력한 사례입니다. 처리 상세, 치환 내역, 복원 응답에서 같은 연락처를 따라갈 수 있습니다.

1. **처리 상세에서 원문과 마스킹 결과를 비교합니다.** 질문 양쪽에는 모두 ‘분석해줘’가 보입니다. 첨부 문서의 첫 번째 연락처에서는 `010-0000-0041`이 `[PHONE_001]`로, `customer041@example.com`이 `[EMAIL_001]`로 바뀝니다.
2. **치환 내역에서 근거를 확인합니다.** 이 요청에는 총 **21건**이 기록됐습니다. 첫 전화번호 행에는 출처 `REGEX`와 문자 범위 `209–222`가, 첫 이메일 행에는 같은 출처와 범위 `249–272`가 표시됩니다.
3. **사용자에게 전달한 답변을 읽습니다.** 이 시연은 데모 응답(Mock) 모드로 실행했습니다. 최종 방문 일정 안내에는 `[PHONE_001]` 자리에 다시 `010-0000-0041`이 나오고, 확정 안내를 받을 이메일도 원래 주소로 표시됩니다.

## 검증 결과
{: #evaluation }

**문서 한 건의 왕복 처리.** 팀은 논문에서 별도의 가상 회의록 TXT를 첨부해 일정과 연락처를 요약하도록 했습니다. 문맥 모델이 이름 두 개를, 정규식이 이메일 두 개와 전화번호 두 개를 찾았습니다. 최종 답변에서 여섯 값이 모두 복원됐고 회의 일정과 후속 작업 기한도 확인했습니다. PDF와 DOCX에서는 여러 페이지와 표를 포함한 문서의 텍스트 추출 순서를 검증했습니다.

**팀의 탐지 모델 평가.** 합성 문서 2,500개 중 최종 시험용 247개에서 한국어 문맥 모델(KLUE-RoBERTa)을 단독으로 평가했습니다. 유형과 시작·끝 위치가 모두 맞은 개인정보는 584건, 오탐은 2건, 미탐은 0건으로 개체 단위 F1은 **99.83%**였습니다. 문서 한 건을 모델이 처리하는 시간의 중앙값은 **1.02초**, 95백분위는 **2.42초**였습니다. 측정 구간은 토큰화부터 탐지 결과를 원문 위치로 되돌리는 단계까지입니다. (졸업논문 표 4.3-1, 표 4.5-1)

**프록시 회귀 테스트.** 입출력 규격을 확인하는 테스트 10개와 프록시 테스트 15개가 모두 통과했습니다. 질문·문서 간 토큰 재사용, 조각으로 나뉜 응답의 복원, 모의 모델을 연결한 요청·응답 흐름을 확인했습니다.

## 느낀 점
{: #lessons }

탐지기가 이메일을 정확히 찾아도 두 서버가 앞의 이모지를 다르게 세면 프록시는 엉뚱한 글자를 가릴 수 있습니다. 이 작업을 하면서 ‘문자 위치’라는 말 하나도 실제 입력과 기대값을 함께 정해야 팀원이 같은 뜻으로 이해할 수 있다는 점을 배웠습니다. PM으로서도 모듈별 완료 보고를 모으는 것만큼, 한 요청이 사용자에게 돌아올 때까지 팀이 함께 확인할 예시를 정하는 일이 중요했습니다.

## 개선할 점
{: #next-steps }

- **전송 직전의 개인정보 검사.** 다음에는 테스트용 수신 서버에서 실제로 받은 질문과 첨부 내용을 대조해, 가상 연락처 원문이 남았는지 확인하고 싶습니다. 논문에서 텍스트 추출까지 확인한 PDF·DOCX도 같은 왕복 검증에 포함할 수 있습니다.
- **토큰 변형과 동시 요청.** 모델이 토큰 철자를 바꾸거나 응답이 끊기면 사용자는 어떤 답을 읽게 되는지 확인할 필요가 있습니다. 두 사용자의 요청에 각각 `[EMAIL_001]`이 생겼을 때도 각자 자기 주소만 돌려받는지 함께 점검하고 싶습니다.
- **첫 복원 응답까지의 시간.** 사용자가 기다리는 시간에는 모델 추론 외에 문서 추출과 답변 생성도 포함됩니다. 파일 업로드부터 첫 번째 복원 문장이 표시될 때까지 구간별로 재면 어디를 먼저 개선할지 판단할 수 있습니다.
